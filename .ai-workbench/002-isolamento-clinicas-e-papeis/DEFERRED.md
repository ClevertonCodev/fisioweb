# Adiado · 002 Isolamento entre clínicas e papéis

- **Histórico do paciente na agenda v2 (feature 005).** O endpoint `GET /api/clinic/patients/{patient}/appointments` deixa o fisioterapeuta ver o histórico completo de um paciente com quem ele tem ao menos uma consulta não cancelada. Ao implementar "fisio vê só os pacientes dele" (agora fora da 002, em `papeis-fora-do-escopo.md`), decidir se essa regra passa a ser "paciente acessível" (responsável ou vínculo em `patient_care_links`). Registrado em 2026-10-17.
- 2026-11-08 · refinar · **As regras de papel e a refatoração estrutural do plano de 2026-10-15 saíram da 002.** Estão descritas em `papeis-fora-do-escopo.md`: secretária só lê o prontuário (hoje ela consegue anexar arquivo), responsável obrigatório, vínculo fisio-paciente, fisio vê só os dele, checagem única de clínica, `Gate::before` mais estreito e trava de arquitetura.
- 2026-11-08 · refinar · **O link de primeiro acesso vale só para o mestre.** Os usuários que o admin da clínica cadastra continuam com a senha digitada pelo admin. Avaliar o mesmo link para eles.
- 2026-11-08 · refinar · **As fotos de paciente e de usuário continuam públicas no R2**, com URL fixa no CDN. Elas têm a mesma raiz do achado dos arquivos do prontuário. Avaliar o link assinado também para elas (isso muda todos os lugares que mostram avatar).
- 2026-11-08 · refinar · **Os brokers de reset de admin e de clínica dividem a mesma tabela** de tokens. Hoje um principal não ganha nada sobre o outro, porque o token vai para a mesma caixa de e-mail. Separar as tabelas quando o e-mail funcionar.
- 2026-11-08 · refinar · **A troca de e-mail do usuário da clínica não pede nova verificação.** Ela deixa ocupar o e-mail de uma pessoa de fora, e o efeito é só de disponibilidade. Depende de o sistema enviar e-mail.
- 2026-11-08 · 002-troca-de-senha-derruba-sessoes · **Sessão aberta no mesmo segundo da troca de senha sobrevive.** O `iat` do JWT é em segundos, e o token só é recusado quando `iat < password_changed_at`, porque o token novo de quem trocou a própria senha nasce no mesmo segundo. O token da própria requisição vai para a blacklist. Uma outra sessão aberta exatamente no mesmo segundo continua valendo. Risco aceito: a janela é de 1 segundo. Duas condições (revisão adversária, achado 003): o token que sobra continua renovável até o `refresh_ttl` (14 dias), porque o refresh mantém o `iat`; e a janela só fica em 1 segundo com `JWT_REFRESH_IAT=false` (o padrão). Com `true`, quem renova em laço mantém um token com o `iat` do segundo da troca. Não ligar `JWT_REFRESH_IAT` sem rever a regra (ou travar com teste).
- 2026-11-08 · 002-troca-de-senha-derruba-sessoes · **Para a tarefa 008 (`impersonated_by`):** o token novo que a edição de usuário devolve a quem troca a própria senha (`ClinicAuthenticatedController::reissueClinicToken`) é emitido sem claims extras. Quando a 008 puser `impersonated_by` no token do "entrar como", o token reemitido precisa levar a mesma claim, senão a troca de senha feita pelo operador "limpa" a marca.
- 2026-11-08 · 002-troca-de-senha-derruba-sessoes · **O aviso "sua sessão expira em 5 minutos" segue o token antigo** depois de trocar a própria senha: o `AuthContext` agendou o aviso pelo `exp` do token do login. O "Renovar" funciona (usa o token novo salvo); só o aviso pode aparecer antes da hora. Avaliar reagendar o aviso quando o token salvo muda.
- 2026-11-08 · 002-troca-de-senha-derruba-sessoes (revisão adversária, achado 004) · **Corrida no SPA ao trocar a própria senha.** Se outra requisição sair com o token antigo durante o PUT e a resposta 401 dela voltar antes da resposta do PUT, o interceptor do `apiClient` renova com o token antigo, recebe 401 e manda para o login. Raro (a tela de edição quase não faz requisição em paralelo). Correção possível: o interceptor tenta de novo com o token salvo quando ele mudou desde que a requisição saiu.
